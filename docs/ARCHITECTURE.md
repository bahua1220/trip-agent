# 架构与约束

## 规划链路

1. 客户端收集目的地、日期、偏好、交通方式、抵离时间及枢纽；多城市可先确认路线。
2. FastAPI 校验输入与身份，创建持久化后台任务，返回任务编号；前端轮询状态。
3. 搜索真实 POI，筛除非景点和重复别名，按区域归并、打分与预算截断候选。
4. 结合酒店、天气与模型建议确定每日游览候选，再搜索周边餐饮。
5. 计算本地交通与跨城衔接，在可用时间内安排游览、用餐、住宿和抵离事件。
6. 执行时段、营业时间、重复、衔接与强度检查；有限修复后仍有硬冲突则不发布不安全结果。
7. 返回时间轴和质量报告，保存历史；编辑请求使用独立规划实例并重新校验。

实际链路有重排、补位和兜底分支，不是严格只走一遍的直线流水线。主要业务规则目前集中在较大的 `trip_planner_agent.py` 中，这是后续模块化重构的重点，不应包装成已经完全解耦的架构。

## 模型与程序的职责

模型用于候选选择、路线建议、结构化内容及天气风险解释；外部工具提供地点、路线和预报。程序承担可确定的时间计算、筛选、去重、时窗与质量校验。不把模型描述当作真实营业时间，也不把估算交通当作已确认班次。

当前使用 LangGraph 的 Agent 图及 LangChain 模型/工具适配，但不是所有步骤都交给自主 Agent 决策，许多关键步骤是显式 Python 编排。

## 状态与并发

- 规划请求与编辑请求创建独立规划实例；候选、餐饮缓存、拒绝列表等不跨用户共享。
- 模型客户端及可复用 Agent 图共享，业务会话状态不共享。
- MySQL 存储账号、身份、历史行程和生成任务；任务执行使用进程内工作线程。
- 当前是单服务工作器的恢复设计，不等于已有多机任务队列、分布式 exactly-once 或无限横向扩容能力。
- 日限额以北京时间自然日计算；具体计数口径以任务服务实现和测试为准。

## 数据边界

- 高德路线不等于实时铁路班次。铁路段为参考用时，异常查询也不构成购票或班次承诺。
- 公共交通耗时不能证明所选时刻一定有车；清晨/深夜会有未核验首末班风险。
- 营业时间可能缺失、解析不完整或过期，预约要求需出发前核实。
- 酒店、票价与餐饮预算是规划参考，不包含支付下单或实时库存保证。
- 缺少真实可用候选时不能靠虚构补齐；失败和降级状态需要如实展示。

## 测试层次

单元/规则回归验证局部条件；固定候选验收验证用户行为约束；HTTP 全流程测试验证路由、任务与保存调用，但身份、数据库和外部供应商仍有替身。显式开启的真实评测用于发现候选与外部数据问题；最后还需体验版真机验收。

因此“离线测试全绿”不能推导为“真实请求没有问题”。新增线上问题应缩减成去标识样本，再补规则测试。
